# Практическое занятие №11: Тестирование приложений

## Написание модульных тестов для FastAPI

На этом занятии мы рассмотрим важность модульного тестирования в приложениях FastAPI и узнаем, как писать модульные тесты для обеспечения корректности и надежности наших веб-API.

**Тестирование** — это не просто поиск багов, а важный инструмент для обеспечения качества кода. Оно помогает:

- Выявлять ошибки на ранней стадии разработки.
- Поддерживать стабильность приложения при внесении изменений.
- Улучшать структуру кода, поскольку тестируемый код обычно пишется более модульно.

Существует несколько типов тестирования:

- **Модульное тестирование** — проверка отдельных компонентов системы (функций, классов, эндпоинтов).
- **Интеграционное тестирование** — проверка взаимодействия нескольких частей системы, например, API и базы данных.
- **Функциональное (системное) тестирование** — проверка работы системы в целом с точки зрения конечного пользователя.

В этом занятии мы сосредоточимся именно на модульных тестах, так как они являются основой для построения надежного кода. Мы разберем, как тестировать конечные точки API, научимся имитировать запросы и ответы, а также рассмотрим подходы к написанию тестов, которые помогут вам избежать ошибок в будущем.

## Что такое модульное тестирование?

**Модульное тестирование** — это процесс изолированного тестирования отдельных модулей или компонентов приложения для проверки их корректной работы. В контексте FastAPI модулем могут быть:

- отдельная конечная точка (эндпоинт API),
- модель данных Pydantic,
- зависимость (Dependency Injection),
- бизнес-логика внутри сервиса.

Главная идея модульного тестирования — проверять каждый компонент **отдельно** от остальных. Это помогает:

- **Быстро находить ошибки** — если тест на конкретный модуль падает, вы сразу знаете, где искать проблему.
- **Упрощать рефакторинг** — можно безопасно менять код, зная, что тесты поймают регрессию.
- **Документировать поведение кода** — хорошо написанные тесты объясняют, как должен работать код.

Чтобы модульные тесты были действительно полезными, важно соблюдать принципы:

- **Изоляция** — тестируемый компонент не должен зависеть от внешних сервисов (например, базы данных).
- **Детерминированность** — результат теста не должен зависеть от внешних факторов (сетевого соединения, времени выполнения).
- **Читаемость** — тесты должны быть понятными, чтобы их можно было использовать как документацию.

В FastAPI модульные тесты позволяют проверить, правильно ли обрабатываются запросы, корректно ли работает валидация данных, а также что API возвращает ожидаемые ответы в разных сценариях.

### Файл настроек Pytest (pytest.ini)

Создайте файл `pytest.ini` в корне проекта. Этот файл необходим для настройки Pytest и управления его поведением. Он помогает задать параметры, которые влияют на поиск тестов, вывод информации и другие настройки. В частности, с его помощью можно указать, какие папки или файлы Pytest должен искать для тестов, как их отображать в выводе и как обрабатывать ошибки.

Пример содержимого `pytest.ini`:

```python
[pytest]
addopts = -v  # Подробный вывод (можно добавить -p no:warnings для отключения предупреждений)
testpaths = tests
pythonpath = . my_app  # Добавляет корень проекта и папку my_app в пути поиска модулей
python_files = test_*.py *_test.py
python_classes = Test*
python_functions = test_*
```

- `testpaths` указывает Pytest, где искать тесты (в нашем случае, в папке `tests`).
- `pythonpath` добавляет пути, которые **Pytest** будет использовать для поиска модулей, чтобы импортировать нужные файлы.
- `python_files`, `python_classes`, `python_functions` — шаблоны имен файлов, классов и функций для поиска тестов.

Файл `pytest.ini` позволяет настроить **Pytest** так, чтобы он правильно находил и выполнял тесты, а также влиял на формат вывода и другие параметры тестирования.

### Файл conftest.py

Файл `conftest.py` используется для создания общих настроек и фикстур, которые могут быть использованы в тестах по всему проекту. Это полезно, когда нужно подготовить тестовую среду (например, создать объекты, которые будут использоваться в тестах) или выполнить действия, которые должны происходить до или после каждого теста.

В нем можно определять фикстуры, которые потом будут автоматически передаваться в тестовые функции как аргументы. Это помогает избежать дублирования кода и улучшить структуру тестов. Например, фикстура может настраивать HTTP-клиент или подключать базу данных для тестов, чтобы в каждом тесте не нужно было повторять одну и ту же логику.

Пример содержимого `conftest.py`:

```python
from fastapi.testclient import TestClient
from my_app.main import app  # Предполагается, что объект app объявлен в my_app/main.py
import pytest

@pytest.fixture
def client():
    return TestClient(app)
```

В этом примере создается фикстура `client`, которая инициализирует объект `TestClient` из FastAPI. Этот объект позволяет тестировать ваше приложение FastAPI, отправляя запросы и получая ответы, как если бы это был реальный клиент. Все тесты, которые будут принимать аргумент `client`, автоматически получат этот объект и смогут использовать его для выполнения запросов.

Использование фикстур в `conftest.py` позволяет централизованно управлять настройками тестовой среды и делает код тестов более чистым и удобным для чтения.

### Фикстуры в Pytest

**Фикстуры** — это мощный механизм в Pytest, который помогает подготовить тестовую среду, управлять ресурсами и гарантировать корректное завершение работы тестов. Они позволяют вынести общие настройки, повторяющиеся действия и очистку после тестов в отдельные функции, чтобы избежать дублирования кода и сделать тесты более понятными и модульными.

**Основные особенности фикстур:**

- **Декоратор @pytest.fixture:** Любая функция, украшенная этим декоратором, становится фикстурой. При вызове тестовой функции Pytest ищет аргументы, совпадающие с именами фикстур, и автоматически передаёт их результаты в тест.
- **Инъекция зависимостей:** Тестовые функции могут принимать в качестве параметров одну или несколько фикстур, что позволяет организовать зависимости между ними. Например, фикстура может создавать базу данных или настраивать HTTP-клиент, который затем используется в нескольких тестах.
- **Скоуп фикстур:** Фикстуры можно настраивать по различным областям видимости (scope):
    - `function` (по умолчанию) – фикстура создаётся для каждого теста.
    - `class` – фикстура создаётся один раз для каждого класса тестов.
    - `module` – фикстура создаётся один раз для каждого модуля.
    - `session` – фикстура создаётся один раз для всей сессии тестирования. Это позволяет оптимизировать выполнение тестов, особенно когда подготовка ресурсов требует значительного времени.

- **Автоматическое завершение (tear-down):** Если необходимо выполнить очистку после использования фикстуры (например, закрыть соединение с базой данных или удалить временные файлы), можно использовать конструкцию yield внутри фикстуры. Код после yield будет выполнен после завершения теста, использующего эту фикстуру.
- **Параметризованные фикстуры:** Pytest поддерживает параметризацию фикстур, что позволяет запускать один и тот же тест с разными данными. Это особенно полезно для проверки работы функции в разных условиях без написания множества отдельных тестов.

### Пример использования фикстуры:

В файле `conftest.py` мы определили фикстуру `client`, которая создаёт экземпляр `TestClient` для тестирования приложения FastAPI. Любая тестовая функция, принимающая параметр `client`, автоматически получает этот объект. Это позволяет тестировать API без необходимости вручную создавать клиент в каждом тесте:

```python
def test_read_main(client):
    response = client.get("/")
    assert response.status_code == 200
```

Таким образом, фикстуры упрощают настройку тестовой среды, делают код более модульным и уменьшают дублирование логики, обеспечивая единообразное создание и очистку необходимых ресурсов.

## Написание первого модульного теста

Теперь, когда тестовая среда настроена, давайте перейдем к написанию первого теста для нашего приложения FastAPI. В этом примере мы создадим тесты для конечной точки, которая вычисляет сумму двух чисел.

Предположим, у нас есть приложение FastAPI с такой конечной точкой:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/sum/")
def calculate_sum(a: int, b: int):
    return {"result": a + b}
```

Фикстура `client` для тестирования, которая использует `TestClient`, уже настроена в файле `conftest.py`.

### 1. Базовый тест

Создадим тест, который будет проверять правильность работы нашей конечной точки с разными входными данными.

```python
def test_calculate_sum(client):
    # Тест 1: валидные входные данные
    response = client.get("/sum/", params={"a": 5, "b": 10})
    assert response.status_code == 200
    assert response.json() == {"result": 15}

    # Тест 2: отрицательные числа
    response = client.get("/sum/", params={"a": -8, "b": -3})
    assert response.status_code == 200
    assert response.json() == {"result": -11}

    # Тест 3: ноль и положительное число
    response = client.get("/sum/", params={"a": 0, "b": 7})
    assert response.status_code == 200
    assert response.json() == {"result": 7}

    # Тест 4: одно число не введено
    response = client.get("/sum/", params={"a": 3})
    assert response.status_code == 422
    assert response.json() == {
        "detail": [
            {
                "loc": ["query", "b"],
                "msg": "field required",
                "type": "value_error.missing"
            }
        ]
    }
```

### 2. Параметризованный тест с использованием `pytest.mark.parametrize`

Для сокращения дублирования кода используем параметризацию тестов. Это позволяет протестировать один и тот же метод с разными входными данными.

```python
import pytest

@pytest.mark.parametrize(
    "a, b, expected_status, expected_result",
    [
        (5, 10, 200, 15),
        (-8, -3, 200, -11),
        (0, 7, 200, 7),
        ("a", 10, 422, None),  # Ошибка валидации: строка вместо числа
        (3, None, 422, None)   # Отсутствует параметр b
    ]
)
def test_calculate_sum_params(a, b, expected_status, expected_result, client):
    params = {"a": a}
    if b is not None:
        params["b"] = b

    response = client.get("/sum/", params=params)
    assert response.status_code == expected_status
    if expected_status == 200:
        assert response.json() == {"result": expected_result}
```

### 3. Тест на ошибку

Важной частью тестирования является проверка ошибок. Например, если мы передаем неверные данные, FastAPI должен вернуть правильный код ошибки (например, **422** для ошибки валидации).

```python
def test_calculate_sum_error(client):
    response = client.get("/sum/", params={"a": "invalid", "b": 10})
    assert response.status_code == 422
```

### 4. Логирование ошибок

Важно не только тестировать успешные сценарии, но и обрабатывать ошибочные случаи. Когда тесты не проходят, полезно добавлять логирование, чтобы легче было найти причину ошибки.

В Pytest можно использовать `pytest.fail()` для принудительного завершения теста с ошибкой и записать сообщение в лог:

```python
def test_calculate_sum_error(client):
    try:
        response = client.get("/sum/", params={"a": "invalid", "b": 10})
        response.raise_for_status()
    except Exception as e:
        pytest.fail(f"Тест не прошел: {e}")
```

### 5. Запуск тестов

Для того чтобы запустить все тесты проекта, используйте команду:

```bash
pytest
```

Если все настроено правильно, вы должны увидеть сообщение, указывающее на то, что тесты пройдены.

Если какие-то тесты не проходят, внимательно посмотрите на сообщения об ошибках и исправьте код. Логирование ошибок и подробные сообщения об ошибках помогут вам быстрее разобраться в причинах неудачных тестов.

## Введение в мокинг (подделку) внешних зависимостей

**Мокинг** (от англ. mock — подделка) — это техника тестирования, при которой реальные зависимости заменяются фальшивыми объектами, имитирующими их поведение. Это позволяет тестировать код изолированно, без реального взаимодействия с базами данных, сторонними API, файловыми системами и другими внешними сервисами.

**Аналогия из жизни**

Представьте, что вы учитесь водить машину. Вместо того чтобы сразу выезжать на оживленную трассу, сначала тренируетесь на симуляторе. Симулятор ведет себя как реальная машина, но при этом вы не рискуете попасть в аварию. Также и в тестировании: мок-объект заменяет настоящую зависимость, создавая безопасную среду для проверки кода.

**Почему это важно в FastAPI?**

В FastAPI, как и в любом другом веб-приложении, часто используются внешние зависимости:

- **Базы данных** (PostgreSQL, MongoDB, SQLite) — без мокинга тестирование может занять больше времени из-за реальных запросов.
- **Сторонние API** (например, платежные системы, погодные сервисы) — если их не заменить на моки, тесты могут зависеть от доступности этих сервисов.
- **Очереди сообщений** (RabbitMQ, Kafka) — мокинг помогает избежать необходимости поднимать реальную инфраструктуру.
- **Работа с файлами** — тесты не должны модифицировать или удалять реальные файлы.

**Как это работает?**

При мокинге реальный объект (например, функция для запроса данных из API) заменяется фальшивым объектом, который заранее знает, что нужно вернуть. Это гарантирует, что тестируемая функция работает предсказуемо, независимо от внешних факторов.

## Потребность в мокинге

При написании модульных тестов важно, чтобы они были быстрыми, надежными и повторяемыми. Однако без мокинга тестирование может превратиться в мучение из-за зависимости от реальных внешних сервисов. Рассмотрим основные проблемы, которые решает мокинг.

### Проблемы тестов без мокинга

- **Медленные тесты** — запросы в базу данных или к внешним API занимают время, увеличивая общее время тестирования.
- **Нестабильность** — внешний сервис может быть временно недоступен, а тесты из-за этого начнут падать.
- **Изменение данных** — если тест работает с реальной БД или API, данные могут меняться, из-за чего тест один раз пройдет, а другой — нет.
- **Ограниченный доступ** — некоторые API требуют авторизации, токенов или даже денег за запросы, что делает тестирование неудобным.

### Схема: реальная зависимость vs мок

| Подход       | Пример теста                                                                 | Потенциальные проблемы                            |
|--------------|------------------------------------------------------------------------------|---------------------------------------------------|
| Без мокинга  | `requests.get("https://api.weather.com")`                                     | API может быть недоступен, тест затянется         |
| С мокингом   | `mock_requests.get.return_value.json.return_value = {"temp": 25}`             | Всегда предсказуемый результат                     |

### Пример реальной проблемы

Представьте, что вы тестируете сервис, который получает курс валют с внешнего API. Если в момент теста пропал интернет, API перестало работать или ответ изменился, ваш тест сломается. Но с мокингом можно заранее задать фиксированный курс валют, чтобы тест всегда работал стабильно.

Поэтому мокинг — это не просто удобство, а необходимость для написания надежных тестов в FastAPI. 

## Использование `unittest.mock` для мокинга

Python предоставляет встроенный модуль `unittest.mock`, который позволяет заменять реальные объекты и функции на **контролируемые моки**. Это особенно полезно при тестировании FastAPI-приложений, где нужно эмулировать работу внешних зависимостей.

### Основные объекты в `unittest.mock`

1. `Mock` — базовый объект для создания заглушек. Позволяет определять поведение методов и атрибутов.
2. `MagicMock` — расширенная версия Mock с поддержкой встроенных методов (`__len__`, `__getitem__`, `__call__ `и т. д.).
3. `patch` — инструмент для временной подмены объектов в тестах. Позволяет заменять функции, классы и модули на моки.

### Минимальный пример использования `MagicMock`

Допустим, у нас есть функция, которая получает текущую температуру через внешний API:

```python
import requests  

def get_temperature():  
    response = requests.get("https://api.weather.com/temp")  
    return response.json()["temp"]
```

В тесте мы не хотим делать реальный запрос, поэтому заменим его `MagicMock`:

```python
from unittest.mock import MagicMock  

mock_response = MagicMock()  
mock_response.json.return_value = {"temp": 25}  

requests.get = MagicMock(return_value=mock_response)  

assert get_temperature() == 25  # Тест всегда будет стабильным
```

### Почему `patch` удобен для FastAPI

Допустим, у нас есть зависимость, которую мы передаем в обработчик:

```python
def get_db():  
    return DatabaseConnection()  
```

Чтобы не создавать реальную базу данных в тесте, можно использовать `patch`:

```python
from unittest.mock import patch, MagicMock  

@patch("__main__.get_db", return_value=MagicMock())  
def test_my_handler(mock_db):  
    db = get_db()  # Теперь это мок, а не реальная БД  
    assert isinstance(db, MagicMock)  
```

Таким образом, `unittest.mock` позволяет легко изолировать код от внешних зависимостей, делая тесты предсказуемыми и быстрыми. 

## Замена внешних зависимостей

В FastAPI внешние зависимости часто внедряются в обработчики и сервисы через механизм зависимостей. В тестах мы хотим заменить их фиктивными объектами, чтобы полностью контролировать их поведение и тестировать различные сценарии без зависимости от реальных данных.

Рассмотрим ситуацию, когда наше приложение получает данные из внешнего API, обрабатывает их и возвращает результат.

### Пример кода с зависимостью от внешнего API

У нас есть модуль, который делает запрос к API и обрабатывает полученные данные:

**external_api.py**

```python
import requests  

def fetch_data_from_api():  
    response = requests.get("https://api.example.com/data")  
    if response.status_code == 200:  
        return response.json()  
    return None  

def process_data(data):  
    # Простая обработка данных: приведение ключей и значений к верхнему регистру  
    return {key.upper(): value.upper() for key, value in data.items()}  
```

Затем этот код используется в приложении:

**app.py**

```python
from external_api import fetch_data_from_api, process_data  

def get_and_process_data():  
    data = fetch_data_from_api()  
    if data:  
        return process_data(data)  
    return None  
```

### Как тестировать `get_and_process_data`, не обращаясь к реальному API?

Если мы запустим тест без мокинга, то столкнемся с несколькими проблемами:

- API может быть недоступно (например, интернет отключен).
- Ответ от API может изменяться, что приведет к нестабильным тестам.
- Тест будет работать медленно из-за сетевого запроса.

Поэтому мы заменим реальный запрос к API мок-объектом и создадим предсказуемые данные.

### Юнит-тест с `unittest.mock`

**test_app.py**

```python
import unittest  
from unittest.mock import patch, MagicMock  
from app import get_and_process_data  

class TestApp(unittest.TestCase):  

    @patch("app.process_data")  # Заменяем обработку данных на фиктивную
    @patch("app.fetch_data_from_api")  # Заменяем реальный API-запрос на мок    
    def test_get_and_process_data(self, mock_fetch_data: MagicMock, mock_process_data: MagicMock):  
        # Аргументы должны отражать порядок декораторов СНИЗУ ВВЕРХ:
        # 1. mock_fetch_data (нижний @patch)
        # 2. mock_process_data (верхний @patch)

        # Подготовка тестовых данных  
        mock_response = {"key": "value"}  
        mock_fetch_data.return_value = mock_response  

        mock_processed_data = {"KEY": "VALUE"}  
        mock_process_data.return_value = mock_processed_data  

        # Вызов тестируемой функции  
        result = get_and_process_data()  

        # Проверяем, что зависимости вызваны правильно  
        mock_fetch_data.assert_called_once()  
        mock_process_data.assert_called_once_with(mock_response)  
        self.assertEqual(result, mock_processed_data)  
```

Как работают моки в этом тесте?

- `patch("app.fetch_data_from_api")` заменяет реальный API-запрос фиктивным объектом `mock_fetch_data`.
- `mock_fetch_data.return_value = mock_response` делает так, что при вызове `fetch_data_from_api()` вернется наш тестовый JSON.
- `patch("app.process_data")` подменяет реальную обработку данных.
- `mock_process_data.return_value = mock_processed_data заставляет process_data()` возвращать фиктивные обработанные данные.
- Мы проверяем, что `fetch_data_from_api` и `process_data` вызываются ровно один раз с правильными аргументами.

### Визуализация потока данных

Чтобы было понятнее, вот схема того, как данные проходят через код и где мы их подменяем:

```text
Реальное API → `fetch_data_from_api()` → `process_data()` → `get_and_process_data()`

            ↓ (МОК)                 ↓ (МОК)
```

Благодаря `unittest.mock`, тесты становятся независимыми от внешних сервисов, выполняются быстро и надежно.

## Лучшие практики для мокинга

Мокинг — мощный инструмент, но его неправильное использование может привести к тестам, которые часто ломаются и требуют постоянного обновления. Чтобы избежать этого, важно понимать, когда стоит применять мокинг, а когда лучше обойтись без него.

**Когда НЕ стоит использовать мокинг?**

- **Для внутренних функций и простых методов**

Если функция или метод не зависят от внешних сервисов, лучше тестировать их напрямую. Например, тестировать process_data() из прошлого примера проще без моков:

```python
def test_process_data():
    input_data = {"key": "value"}
    expected_output = {"KEY": "VALUE"}
    assert process_data(input_data) == expected_output
```

Мокинг в этом случае только усложнил бы код теста без особой пользы.

- **Когда проще использовать тестовую базу данных или локальный сервис**.  
Вместо мокинга базы данных можно использовать SQLite в памяти (`sqlite:///:memory:`) или docker-контейнер с тестовой БД. Это обеспечит более реалистичные тесты.

- **Когда мокинг мешает рефакторингу**.  
Если тесты слишком зависят от структуры кода, то при любом изменении в реализации придется менять и тесты. Лучше мокать **интерфейсы (абстракции)**, а не конкретные методы.

### Советы по написанию надежных тестов с мокингом

1. **Мокайте только внешние зависимости**.  
Если метод взаимодействует с БД, API, файловой системой или очередями сообщений — это кандидат для мокинга.

2. **Избегайте мокинга деталей реализации**.   
Мокать нужно **поведение**, а не реализацию. Например, вместо:

```python
@patch("some_module.SomeClass.some_method")
```

лучше мокать интерфейс:

```python
@patch("some_module.SomeDependency")
```

3. **Используйте `autospec=True`** для лучшей надежности моков.      
`autospec` гарантирует, что мок ведет себя как реальный объект, не позволяя вызывать несуществующие методы:

```python
@patch("some_module.SomeDependency", autospec=True)
```

4. **Не бойтесь комбинировать мокинг с тестовыми данными**.  
Иногда удобнее загружать тестовые JSON-файлы вместо мокинга API-ответов.

5. **Следите за корректностью вызовов моков**.   
Проверяйте, что моки вызываются с нужными аргументами:

```python
mock_func.assert_called_once_with(expected_arg)
```

Мокинг помогает ускорить тестирование и сделать его независимым от внешних сервисов, но **использовать его нужно осознанно**. Правильный баланс моков и реальных зависимостей позволит писать поддерживаемые и надежные тесты.

## Исправление внешних функций

В контексте тестирования "исправление" (patching) — это подмена поведения функций или объектов, которые взаимодействуют с внешними сервисами, такими как базы данных или API. Мы не исправляем баги, а временно заменяем реальную логику фиктивными значениями, чтобы контролировать поведение системы в тестах.

### Пример мокирования API-запросов

Допустим, у нас есть функция, которая делает HTTP-запрос:

```python
import requests

def fetch_data():
    response = requests.get("https://api.example.com/data")
    if response.status_code == 200:
        return response.json()
    else:
        return None
```

В тестах нам не нужен реальный запрос, поэтому мы заменим его мокированным ответом:

```python
import unittest
from unittest.mock import patch, MagicMock
from mymodule import fetch_data

class TestAPI(unittest.TestCase):

    @patch("mymodule.requests.get")
    def test_fetch_data_success(self, mock_get: MagicMock):
        # Создаем мокированный ответ
        mock_response = MagicMock()
        mock_response.status_code = 200
        mock_response.json.return_value = {"key": "value"}
        
        # Устанавливаем этот мок как возвращаемое значение requests.get
        mock_get.return_value = mock_response

        result = fetch_data()
        self.assertEqual(result, {"key": "value"})
        mock_get.assert_called_once_with("https://api.example.com/data")
```

Таким образом, даже если API упадет, тесты не сломаются.

### Моделирование ошибок с `side_effect`

Иногда нужно проверить, как код реагирует на ошибки — например, таймаут или статус `500`. Для этого используем `side_effect`:

```python
@patch("mymodule.requests.get")
def test_fetch_data_error(mock_get: MagicMock):
    mock_get.return_value.status_code = 500
    result = fetch_data()
    assert result is None
```

А вот так можно смоделировать таймаут запроса:

```python
import requests

@patch("mymodule.requests.get")
def test_fetch_data_timeout(mock_get: MagicMock):
    mock_get.side_effect = requests.Timeout
    with self.assertRaises(requests.Timeout):  # Проверяем, что исключение пробрасывается
        fetch_data()
```

С `side_effect` можно подставлять разные ошибки или разные результаты:

```python
mock_get.side_effect = [requests.Timeout, MagicMock(status_code=200, json=lambda: {"data": "ok"})]
```

В этом случае первый вызов `requests.get` вызовет `Timeout`, а второй — вернет успешный ответ.

### Пример с повторными запросами

Если функция `fetch_data()` выполняет несколько попыток при ошибке (например, повторные запросы), использование списка в `side_effect` оправдано. Например:

```python
# Пример для функции с повторными запросами
def fetch_data(retries=2):
    for _ in range(retries):
        try:
            response = requests.get("https://api.example.com/data")
            if response.status_code == 200:
                return response.json()
        except requests.Timeout:
            continue
    return None

@patch("mymodule.requests.get")
def test_fetch_data_retry(mock_get: MagicMock):
    # Первый вызов — таймаут, второй — успешный ответ
    mock_get.side_effect = [requests.Timeout, MagicMock(status_code=200, json=lambda: {"data": "ok"})]
    result = fetch_data(retries=2)
    assert result == {"data": "ok"}
    assert mock_get.call_count == 2
```

Использование `patch` и `side_effect` позволяет гибко контролировать поведение внешних зависимостей, тестируя сценарии успеха, ошибок и исключений. Это делает тесты более надежными и предсказуемыми.

## Проверка вызовов функций

Помимо подмены зависимостей, в тестах важно проверять, какие функции вызываются и с какими аргументами. Это помогает убедиться, что код работает правильно, например:

- API-запрос действительно выполняется.
- Кеширование работает, и повторные запросы не отправляются.
- Обработчики ошибок вызываются при сбоях.

Библиотека `unittest.mock` предоставляет методы:

- `assert_called_once()` — проверяет, что функция была вызвана ровно один раз.
- `assert_called_with(*args, **kwargs)` — проверяет, что функция была вызвана с конкретными аргументами.
- `assert_not_called()` — убеждается, что функция не была вызвана.
- `assert_called_once_with(*args, **kwargs)` — проверяет, что функция была вызвана один раз с конкретными аргументами.
- `assert_called()` — проверяет, что функция была вызвана хотя бы раз.
- `call_count` — показывает количество вызовов функции.

### Пример: проверяем вызовы в тесте

Перепишем тест, сделав его чище:

```python
import unittest
from fastapi.testclient import TestClient
from main import app
from unittest.mock import patch, MagicMock

client = TestClient(app)

class TestMain(unittest.TestCase):

    @patch("main.fetch_data_from_api")
    @patch("main.process_data")
    def test_get_and_process_data(self, mock_process_data, mock_fetch_data):
        # Подготавливаем мокированные данные
        mock_response = {"key": "value"}
        mock_processed_data = {"KEY": "VALUE"}
        
        # Настраиваем поведение моков
        mock_fetch_data.return_value = mock_response
        mock_process_data.return_value = mock_processed_data

        # Выполняем запрос
        response = client.get("/data/")

        # Проверяем вызовы функций
        mock_fetch_data.assert_called_once()
        mock_process_data.assert_called_once_with(mock_response)
        
        # Проверяем ответ API
        self.assertEqual(response.status_code, 200)
        self.assertEqual(response.json(), mock_processed_data)
```

Мы отделили подготовку моков от проверок, сделав код теста более читаемым.

### Дополнительные проверки вызовов

**Проверяем, что функция не была вызвана**

Допустим, у нас есть кеширование, и функция 
`fetch_data_from_api` не должна вызываться повторно:

```python
mock_fetch_data.assert_not_called()
```

**Проверяем количество вызовов (call_count)**

Иногда важно убедиться, что функция была вызвана несколько раз, например, при ретраях:

```python
self.assertEqual(mock_fetch_data.call_count, 3)  # проверяем, что запрос отправился трижды
```

**Проверяем конкретные аргументы вызова**

Если функция вызывается несколько раз, можно проверить конкретные аргументы каждого вызова:

```python
from unittest.mock import call

mock_process_data.assert_has_calls([call({"key": "value"}), call({"another_key": "another_value"})])
```

Проверка вызовов функций делает тесты более надежными и помогает гарантировать, что код выполняет нужные операции. Особенно полезно это в ситуациях с кешированием, ретраями и сложной логикой обработки данных.
